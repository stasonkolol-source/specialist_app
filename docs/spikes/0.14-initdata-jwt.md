## Итог

**Алгоритм подписи — EdDSA (Ed25519).** Запасной ES256 не понадобился: PyJWT подписывает и проверяет EdDSA через `cryptography`, а токены проверяет только backend, клиентам алгоритм не важен. Ключ Ed25519 — 32 байта, поэтому он помещается в одну строку `.env` без PEM.

| Вектор плана | Результат |
|---|---|
| Валидный initData (эталонный хэш сверен с `aiogram.utils.web_app.check_webapp_signature`) | ✓ |
| Просроченный `auth_date` (старше 1 ч) → `init_data_expired`; из будущего больше 60 с → `invalid_init_data` | ✓ |
| Подменённое поле (`user`, `auth_date`, `signature`) | ✓ отвергнут |
| Чужой бот; секрет Login Widget (`SHA256(token)`) вместо `WebAppData` | ✓ отвергнут |
| Нет `hash`, пустой или короткий `hash`, повтор ключа, мусор, строка длиннее 8 КБ | ✓ отвергнут |
| JWT: истёк; чужой `kid`; чужая подпись под тем же `kid`; подмена клеймов; `alg=none`, HS256 и ES256 вместо EdDSA; чужой `iss` | ✓ отвергнут |
| Ротация ключей: токен старого ключа проходит, пока ключ в `JWT_KEYS` | ✓ |
| Refresh: ротация при каждом использовании; повтор старого токена отзывает сессию и кладёт `sid` в denylist | ✓ |

## Решения — правила для кода

1. **Ключи JWT — в `JWT_KEYS`**, формат `kid:ключ,kid:ключ`, ключ — base64url 32 байт приватного Ed25519. Первый ключ подписывает, остальные только проверяют. `make cli ARGS=jwt-keys` создаёт ключ, если его нет; повторный запуск ничего не меняет; `--rotate` ставит новый ключ первым и оставляет один предыдущий (выданные им access-токены живут ещё 15 минут). Значения команда не печатает. Для stage и prod владелец запускает её на своей машине с `--env-file` и переносит значение в секреты Kamal (K10a). `JWT_KEYS_DIR` из шага 0.4 заменён на `JWT_KEYS`.
2. **Время токена проверяем по порту Clock, а не часами PyJWT** (`verify_exp=False` и своя проверка `exp`). Так тесты управляют временем через `FakeClock`, а PyJWT проверяет только подпись, `iss` и наличие клеймов. Допуска на `exp` нет: access короткий, клиент обновляет его заранее.
3. **`kid` обязателен.** Токен без `kid` или с незнакомым `kid` отвергается до проверки подписи. Список алгоритмов при проверке — только `EdDSA`, поэтому подмена `alg` невозможна.
4. **Коды 401** (все — `NotAuthenticatedError`, `platform/security/errors.py`), по ним клиент решает, что делать:

   | `code` | Действие клиента |
   |---|---|
   | `token_expired` | `POST /auth/refresh` |
   | `invalid_token`, `session_revoked`, `invalid_refresh_token` | Новый вход: в Mini App — обмен свежего initData |
   | `init_data_expired` | Mini App открыт больше часа назад: `Telegram.WebApp` перезапускается, либо используем refresh |
   | `invalid_init_data` | Ошибка входа (S49) |

5. **initData.** В data-check-string входят все поля, кроме `hash`, в том числе `signature` (research/02 §3.2). Регистр `hash` не важен. Повтор ключа в строке — отказ: `parse_qsl` иначе молча взял бы последнее значение. Без `user` войти нельзя (inline-режим). Ошибки не содержат ни строки, ни полей initData. Токен бота берётся из `TelegramSettings` окружения, поэтому initData dev-бота на stage не пройдёт.
6. **Refresh-токен — `<sid>.<secret>`.** `sid` — hex UUIDv7 сессии, `secret` — 256 бит `token_urlsafe(32)`; в БД — только SHA-256 секрета, сверка `hmac.compare_digest`. Префикс `sid` даёт поиск сессии по первичному ключу и отличает повтор старого токена от незнакомого.
7. **Ротация и детектор кражи (переносится в агрегат сессии identity в 0.15a).** В сессии хранятся хэш текущего секрета, хэш предыдущего и `rotated_at`:
   - совпал текущий — выдаём новый токен, текущий хэш становится предыдущим, срок продлевается;
   - совпал предыдущий не позже 10 с после ротации — 401 `invalid_refresh_token` **без отзыва**. Это повтор запроса, ответ на который потерялся, или два одновременных обновления. Mini App после этого снова обменяет initData;
   - иначе (старый токен или подбор секрета при известном `sid`) — отзыв всей сессии и `sid` в denylist.

   Отзыв при подборе с известным `sid` безопасен: `sid` виден только владельцу access-токена, а утёкший access — уже компрометация. Api-client (0.20) делает обновление single-flight: одно на все параллельные 401.
8. **Denylist `sid` — ключ `auth:revoked:<sid>` в Valkey на `JWT_ACCESS_TTL_SECONDS`.** Проверка Bearer (0.15b) отвергает токены отозванной сессии сразу, не дожидаясь `exp`. Refresh отзывается в БД.
9. **Сроки refresh.** 7 дней для Mini App (`JWT_REFRESH_TTL_DAYS_TMA`), 30 для мобильных приложений (`JWT_REFRESH_TTL_DAYS`), по ADR-0009.
