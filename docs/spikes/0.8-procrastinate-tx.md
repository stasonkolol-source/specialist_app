- **Дата:** 2026-09-27
- **Шаг плана:** [0.8](../DEVELOPMENT_PLAN.md#08-спайк-транзакционная-постановка-задач-procrastinate)

## Итог

**Механизм ADR-0008 работает: задача ставится на соединении сессии SQLAlchemy, в той же транзакции, что и данные.** Запасной план (таблица `platform.outbox` и relay) не нужен. Шаг 0.10 пишет адаптер `ProcrastinateJobQueue`.

| Сценарий плана | Результат |
|---|---|
| Rollback отменяет и данные, и задачу | ✓ |
| Commit делает задачу видимой: до commit её не видит ни пул, ни воркер; после — NOTIFY `procrastinate_any_queue_v1` и выполнение воркером | ✓ |
| `queueing_lock` даёт `AlreadyEnqueued`, бизнес-транзакция при этом не ломается (под savepoint psycopg) | ✓ |
| Воркер на `psycopg_pool` (PsycopgConnector) выполняет 20 задач с concurrency 4 | ✓ |

Как ставить задачу на соединении сессии:

```python
conn = await session.connection()
driver = (await conn.get_raw_connection()).driver_connection   # psycopg.AsyncConnection
async with driver.transaction():                                # SAVEPOINT: соединение уже в транзакции
    await task.configure(connection=driver, queueing_lock=key).defer_async(**payload)
```

## Находки — правила для кода

1. **Savepoint — на уровне psycopg, не SQLAlchemy.** `session.begin_nested()` отправляет `SAVEPOINT` лениво — только когда внутри выполнится команда самого SQLAlchemy. Вставка Procrastinate идёт мимо SQLAlchemy по тому же соединению, поэтому никакого savepoint нет. Адаптер `JobQueue` оборачивает каждую постановку в `driver.transaction()`: psycopg сразу шлёт `SAVEPOINT` и откатывается к нему при ошибке. `AlreadyEnqueued` адаптер считает успехом — задача уже стоит.
2. **Тихий `ROLLBACK` вместо `COMMIT` (опасно).** Если транзакция в состоянии ошибки (`INERROR`), PostgreSQL отвечает на `COMMIT` командой `ROLLBACK`, а SQLAlchemy не бросает исключения: «успешный» commit теряет и данные, и задачи. **Правило UoW (шаг 0.10):** перед `COMMIT` проверить `driver.info.transaction_status`; если `INERROR` — `ROLLBACK` и исключение (ошибка программиста), а не commit. Тест `test_sqlalchemy_savepoint_is_lazy_and_commit_silently_rolls_back` фиксирует поведение.
3. **Схема `procrastinate`.** SQL Procrastinate создаёт объекты без префикса схемы. Их ставим в отдельную схему `procrastinate` под ролью `migrator` (миграция в шаге 0.9), а роли `app` и `migrator` получают `search_path = public, procrastinate` на уровне роли в `infra/postgres/bootstrap.sql`: функции Procrastinate вызываются без схемы и должны находиться с любого соединения — и из пула воркера, и с соединения сессии SQLAlchemy.
4. **LISTEN/NOTIFY работает под ролью `app`** — отдельных прав не нужно.
5. **Только `SET LOCAL` на соединениях из пула.** Обычный `SET` живёт до конца сессии: соединение вернётся в пул с чужими параметрами. В спайке `SET search_path` на соединении `migrator` сломал следующий тест («type geography does not exist»). Параметры сеанса — `SET LOCAL` внутри транзакции или параметры роли и строки подключения.
