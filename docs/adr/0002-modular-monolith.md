# ADR-0002: Модульный монолит с границами доменов

- **Статус:** принято
- **Дополнено** [ADR-0019](0019-goods-section-module-deferred.md) (раздел «Вещи», после MVP, итерация «Вещи»): 17-й модуль `goods`; read-model и `GoodsSearchPort` вещей живут в `goods`, а не в `search` (отступление от п. 6).
- **Дата:** 2026-09-26
- **Связанные документы:** [ARCHITECTURE.md §5](../ARCHITECTURE.md#5-модульная-структура-backend), [ADR-0003](0003-api-first-rest-openapi.md), [ADR-0008](0008-background-jobs-and-outbox.md)

## Контекст

- **Команда.** 1–2 Python-разработчика, бюджет стартапа.
- **Домен.** Маркетплейс с двумя сторонами: каталог специалистов, доска заявок, отклики, сделки, отзывы, чат, уведомления, модерация, биллинг. Домен ещё будет меняться: границы между «заявкой», «откликом» и «сделкой» уточнятся после первых сотен реальных сделок.
- **Инварианты.** Некоторые бизнес-действия атомарны по своей природе: принятие отклика одновременно меняет заявку, все её отклики и создаёт сделку.
- **Нагрузка.** На горизонте года — сотни RPS на пике (см. ARCHITECTURE.md §2).
- **Клиенты.** Telegram-бот, Mini App, в будущем нативное приложение и админка. Все ходят в один backend (API-first).

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Классический монолит без границ** («всё в одном `models.py`») | Быстрый старт | Через 6–12 месяцев — «большой ком грязи»: любое изменение задевает всё, выделить часть в сервис невозможно |
| **B. Микросервисы с первого дня** | Независимые деплои и масштабирование | Распределённые транзакции (саги) для базовых сценариев, N пайплайнов и сервисов в мониторинге, сетевые отказы, контрактное тестирование. Для 1–2 человек это прямой путь не выпустить MVP |
| **C. Модульный монолит**: один деплой, строгие границы модулей | Скорость монолита + подготовленные швы для выделения | Нужна дисциплина и автоматическая проверка границ |

## Решение

Строим **модульный монолит** (вариант C) со следующими правилами:

1. **Модули.** 16 модулей — 15 доменных плюс shared kernel `platform`; каждый — bounded context: `platform`, `identity`, `geo`, `catalog`, `media`, `billing`, `specialists`, `pricing`, `deals`, `jobs` (включая отклики), `messaging`, `reviews`, `search`, `growth`, `notifications`, `moderation`. Плюс интерфейсный слой (`admin`, HTTP, бот, воркеры).
2. **Схема на модуль.** У каждого модуля своя схема PostgreSQL; менять данные модуля может только сам модуль.
3. **Фасады.** Публичный контракт модуля — фасад (`api.py`). Импорт внутренностей чужого модуля запрещён и проверяется в CI (`import-linter` или `tach`).
4. **Направление зависимостей.** Модули образуют DAG. Синхронные вызовы фасадов и FK между схемами разрешены только «вниз» по DAG.
5. **События.** Доменные события идут в любую сторону через общий пакет контрактов и transactional outbox ([ADR-0008](0008-background-jobs-and-outbox.md)).
6. **Композитные экраны** собираются в интерфейсном слое (BFF) или в read-model модуля `search`.
7. **Один артефакт сборки** (Docker-образ), несколько процессов: `web`, `bot`, `worker`, `worker-media`. Периодические задачи выполняет очередь задач, отдельный scheduler не нужен ([ADR-0008](0008-background-jobs-and-outbox.md)).

## Последствия

**Положительные**

- Одна транзакция там, где нужен инвариант; никаких саг в MVP.
- Один деплой, одна локальная среда (`docker compose up`), один набор логов и трейсов.
- Рефакторинг границ — это изменение кода, а не миграция между базами.
- Для выделения модуля в сервис есть готовые швы: фасад (подменяется HTTP/gRPC-клиентом), события (relay переключается на брокер), своя схема (переезжает в отдельную БД).

**Отрицательные и риски**

- Нужна дисциплина: без автоматической проверки импортов границы размоются. Смягчение — линтер архитектуры в CI с первого коммита.
- Все модули масштабируются вместе. Смягчение — отдельные очереди и пулы воркеров для тяжёлых задач (`media`, `notifications`).
- Общая БД — общая точка отказа. Смягчение — бэкапы с PITR, read replica по мере роста (ARCHITECTURE.md §16, §18).

**Что сделать**

- Настроить контракты `import-linter`/`tach` в первом же PR со скелетом проекта.
- Описать DAG модулей в конфиге линтера. Этот конфиг — единственный источник правды: схема в §5.4 ARCHITECTURE.md должна ему соответствовать.
- Критерии выделения сервиса описаны в ARCHITECTURE.md §5.6. Без измеримой причины модули не выделяем.
