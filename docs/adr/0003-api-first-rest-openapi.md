# ADR-0003: API-first — REST + OpenAPI 3.1, версия в пути

- **Статус:** принято
- **Дата:** 2026-09-26
- **Связанные документы:** [ARCHITECTURE.md §8](../ARCHITECTURE.md#8-api-дизайн), [ADR-0009](0009-authentication-and-identity.md), [ADR-0012](0012-mini-app-frontend-and-mobile-path.md)

## Контекст

Сейчас у платформы два клиента: Telegram Mini App (веб в WebView) и Telegram-бот. Потом появятся нативные iOS/Android-приложения и, возможно, публичный веб-сайт. Бизнес-логика должна жить только в backend, чтобы переход на мобильное приложение не требовал её переписывать. Мобильные клиенты обновляются медленно: пользователи неделями живут на старых версиях. Значит, API должен эволюционировать без поломок.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| **REST + OpenAPI** | Понятен всем, кэшируется HTTP-средствами, отличная генерация типизированных клиентов (TypeScript, Swift, Kotlin), простая отладка | Для составных экранов нужны BFF-эндпоинты |
| **GraphQL** | Гибкие выборки для разных клиентов | Сложнее кэширование, rate limiting и авторизация на уровне полей. Для 1–2 разработчиков — лишний слой. Экранов немного, их удобнее обслуживать BFF-эндпоинтами |
| **gRPC / Connect** | Строгие контракты, стриминг | Хуже поддержка в браузере и WebView Telegram, сложнее отладка; нужен прокси или Connect |
| **tRPC** | Отличный DX в TypeScript-монорепо | Требует TypeScript на backend — противоречит вводной «backend на Python» |

## Решение

- **Стиль.** REST поверх HTTPS, JSON, базовый путь `/api/v1`.
- **Контракт.** OpenAPI 3.1 генерируется из кода backend. Это единственный источник правды для клиентов: из схемы генерируются TypeScript-клиент (Mini App, React Native) и при необходимости Swift/Kotlin.
- **Версионирование.**
  - Мажорная версия в пути; внутри версии изменения только аддитивные.
  - Ломающие изменения — новая мажорная версия параллельно со старой.
  - Старая версия поддерживается минимум 6 месяцев после выхода мобильного приложения.
  - Устаревание сообщается заголовками `Deprecation` и `Sunset`.
  - Проверка совместимости схемы (`oasdiff` или аналог) — в CI.
- **Клиент и версии.** Каждый запрос несёт заголовок `X-Client: <platform>/<version>`. `GET /client-config` отдаёт минимальные поддерживаемые версии (forced update) и feature flags.
- **Ошибки** — RFC 9457 Problem Details со стабильным машинным `code`. Текст ошибок локализован.
- **Надёжность.** Пагинация keyset-курсорами; `Idempotency-Key` для создающих POST; `If-Match` для optimistic locking.
- **Композитные экраны** (карточка специалиста) обслуживаются BFF-эндпоинтами в интерфейсном слое, а не цепочкой запросов с клиента.
- **Realtime** (v1) — отдельный канал событий на SSE. Мутации всегда идут через REST. Браузерный `EventSource` не отправляет заголовок `Authorization`, поэтому поток открывается через fetch-стрим с bearer-токеном или по короткоживущему ticket в query.
- **Бот не обращается к REST API по сети.** Он — интерфейсный адаптер внутри того же монолита и вызывает те же application-сервисы, что и HTTP-роутеры. Так у бизнес-логики один источник, без сетевых накладных расходов.

## Последствия

**Положительные**

- Мобильное приложение подключается к уже существующему API; меняются только клиенты.
- Типизированный клиент из OpenAPI убирает целый класс ошибок интеграции и ускоряет фронтенд.
- Проверка обратной совместимости автоматическая, а не «на глаз».

**Отрицательные и риски**

- BFF-эндпоинты нужно поддерживать в синхронизации с экранами. Смягчение — BFF только для 3–5 «тяжёлых» экранов; остальное — ресурсные эндпоинты.
- Жёсткая дисциплина аддитивных изменений. Смягчение — линтер схемы в CI и правило «новое поле опционально, пока все клиенты не обновились».

**Что сделать**

- Настроить генерацию OpenAPI и публикацию схемы как артефакта CI.
- Завести пакет `packages/api-client` во фронтенд-монорепо с автогенерацией клиента.
- Зафиксировать в `CONTRIBUTING.md` правила эволюции API.
