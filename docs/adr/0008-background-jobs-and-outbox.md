# ADR-0008: Фоновые задачи и доменные события — Procrastinate (очередь в PostgreSQL)

- **Статус:** принято (с обязательным спайком — см. «Что сделать»)
- **Дата:** 2026-09-26
- **Связанные документы:** [research/03-backend-stack.md §4](../research/03-backend-stack.md#4-фоновые-задачи), [ADR-0002](0002-modular-monolith.md), [ARCHITECTURE.md §12](../ARCHITECTURE.md#12-фоновые-задачи)

## Контекст

Многое в продукте происходит асинхронно:

- рассылка новых заявок подписанным исполнителям — fan-out с лимитами Telegram около 30 msg/s;
- обработка фото и видео;
- пересчёт read-model поиска;
- автопроверки модерации;
- напоминания и истечение сроков;
- удаление данных по запросу.

Изменение данных и постановка задачи должны быть **атомарны**: заявка опубликована ⇔ рассылка гарантированно будет. Классическая связка «БД + брокер в Redis» даёт проблему двойной записи (dual write): задача теряется при падении между commit и отправкой в брокер или стартует раньше commit. Лечится она transactional outbox — это отдельная таблица и relay-процесс.

Нагрузка на горизонте года — тысячи, в пиках десятки тысяч задач в час. Это далеко от пределов очереди на PostgreSQL.

## Рассмотренные варианты

| Вариант | Оценка |
|---|---|
| **Procrastinate 3.10** (очередь в PostgreSQL) | Задача ставится **на соединении приложения внутри его транзакции** (с 3.8), то есть строка задачи и есть outbox-запись. Нативный asyncio, retry-стратегии, `@periodic` с HA при нескольких воркерах, `queueing_lock`/`lock` для идемпотентности и сериализации. Минусы: проект ищет мейнтейнеров, зависшие после SIGKILL задачи надо возвращать периодической задачей, мониторинг незрелый, пропускная способность — сотни задач/с |
| Taskiq 0.12 + Valkey Streams | Нативный asyncio, интеграции с dishka и aiogram, метрики. Но нужен свой outbox (таблица + relay), scheduler строго в одном экземпляре |
| Celery 5.6 | Нет asyncio, «time and fund shortage» у проекта |
| arq 0.28 | Maintenance-only с 2025-10 |
| Dramatiq, SAQ | Слабее async-модель или нет постановки в транзакции приложения |
| Temporal, Hatchet | Отдельный сервер; избыточно до появления многошаговых платёжных процессов |

## Решение

1. **Очередь задач — Procrastinate 3.10** на той же базе PostgreSQL (отдельная схема `procrastinate`).
2. **Порт `JobQueue`** в `platform`. Прикладной код вызывает только `enqueue(task, payload, dedup_key)` и ничего не знает о Procrastinate.
3. **Доменные события.** Use case регистрирует событие в Unit of Work. При commit диспетчер **в той же транзакции** ставит по одной задаче на каждого подписчика события (например, `JobPublished` → `jobs.match_alerts`, `search.reindex_job`, `moderation.auto_check`). Отдельной таблицы outbox нет: её роль играет таблица задач.
4. **Очереди и воркеры:**

   | Очередь | Что в ней | Где обрабатывается |
   |---|---|---|
   | `default` | Обработчики событий, read-model, модерация | Процесс `worker` |
   | `notifications` | Fan-out и отправка в Telegram | Процесс `worker`, ограниченная concurrency и глобальный rate limiter в Valkey |
   | `media` | Pillow, ffmpeg | Отдельный процесс `worker-media` с лимитами CPU и памяти |

5. **Периодические задачи** — `@app.periodic` внутри воркеров (HA без отдельного scheduler). Среди них служебные: `retry_stalled_jobs` (возврат зависших задач) и `remove_old_jobs` (ретеншн выполненных задач — 7 дней).
6. **Идемпотентность — всегда.** Доставка at-least-once, поэтому:
   - `queueing_lock` по ключу сущности;
   - уникальные ограничения в БД (`dedupe_key` уведомлений, `(channel, external_id)` платежей);
   - проверка текущего состояния перед действием.
7. **Retry** — экспоненциальный с джиттером, до 5–8 попыток. Дальше задача переходит в статус `failed`, срабатывает алерт в Sentry и метрика.

## Последствия

**Положительные**

- Нет dual write и не нужно отдельно писать outbox и relay: атомарность «данные + задача» даёт PostgreSQL.
- Меньше инфраструктуры: брокер для задач не нужен, Valkey остаётся только для кэша, лимитов и FSM бота.
- Задачи видны SQL-запросом; бэкап БД включает и очередь.

**Отрицательные и риски**

| Риск | Смягчение |
|---|---|
| Транзакционная постановка через соединение SQLAlchemy async (psycopg) подтверждена только чтением исходников | Первая задача спайка — интеграционный тест. Если не работает — таблица `platform.outbox` + relay (`SELECT … FOR UPDATE SKIP LOCKED`), интерфейс `JobQueue` не меняется |
| Нагрузка очереди на PostgreSQL (vacuum таблиц задач) | Ретеншн, мониторинг bloat. При росте за сотни задач/с — Taskiq + Valkey Streams + outbox за тем же портом |
| Малочисленные мейнтейнеры Procrastinate | Порт `JobQueue` делает замену механической; объём зависимости небольшой |
| Незрелый мониторинг | Свои метрики: лаг очереди, возраст старейшей задачи, число `failed`, длительность по типам задач |

**Что сделать**

1. Спайк: SQLAlchemy `AsyncSession` → `connection.get_raw_connection().driver_connection` → `task.configure(connection=…)` → rollback транзакции должен удалить задачу, commit — сделать её видимой воркеру.
2. Обёртка задач: scope dishka, structlog-контекст (`job_id`, `event_id`), Sentry-интеграция (готовой для Procrastinate нет).
3. Метрики очередей в Prometheus и алерты: лаг > 2 мин для `notifications`, любые `failed`.
