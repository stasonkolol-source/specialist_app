# ADR-0010: Общение клиента и исполнителя — гибрид: свой backend переписки + Telegram как канал доставки

- **Статус:** принято
- **Дополнено** [ADR-0019](0019-goods-section-module-deferred.md) (раздел «Вещи», после MVP, итерация «Вещи»): `kind='listing'`, роли `seller` / `buyer`, сообщение `tracking`, бронь как аналог «Договорились».
- **Поправка 2026-10-04** (решение владельца): если эта пара уже договаривалась — в любом диалоге, — контакты открыты. Подробности — в разделе «Поправка 2026-10-04» в конце.
- **Дата:** 2026-09-26
- **Связанные документы:** [research/02-telegram-platform.md §4.4](../research/02-telegram-platform.md#44-топики-в-личных-чатах-и-relay-чат-клиент--исполнитель), [ARCHITECTURE.md §11](../ARCHITECTURE.md#11-уведомления-и-realtime), [ADR-0011](0011-telegram-bot-integration.md), [ADR-0016](0016-trust-safety-and-reviews.md)

## Контекст

После отклика или обращения из каталога клиенту и исполнителю нужно договориться: уточнить задачу («какая люстра, есть ли крюк?»), время и цену. Ограничения:

- **Не у всех есть username.** У многих пользователей Telegram нет публичного username, а `tg://user?id=` открывает чат не при всех настройках приватности. Простой «переход в личку» работает не всегда.
- **Нужен контроль платформы.** Переписка внутри платформы даёт:
  - детекцию мошенничества: ссылки, просьбы о предоплате, обмен телефонами до сделки;
  - подтверждение факта сделки — это основа проверенных отзывов;
  - разбор споров.
- **Этап 2.** В iOS-приложении нужен собственный чат: механизмы Telegram туда не переносятся.
- **Топики бота.** В Telegram с Bot API 9.3–9.4 есть топики в личных чатах с ботом. Но пока режим включён, Telegram удерживает **15% со всех покупок за Stars** в этом боте, а мы планируем монетизацию через Stars ([ADR-0014](0014-monetization-and-billing.md)).
- **Бюджет MVP** ограничен.

## Рассмотренные варианты

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| A. Только обмен контактами | После выбора исполнителя показываем `@username` или телефон | Минимум работы | Нет Q&A до выбора; не работает без username; сделка уходит из продукта; нет данных для антифрода и отзывов |
| B. Relay через топики бота | Один топик на диалог в личке каждого участника, сообщения копируются ботом | Нативный UX Telegram без своего UI | −15% со всех Stars-покупок; зависит от версии клиента; в iOS не переносится |
| C. Свой чат в Mini App + уведомления ботом | Переписка в нашем backend, UI в Mini App, бот присылает «новое сообщение» | Полный контроль; тот же API для iOS | Больше работы (UI, realtime) |
| **D. Гибрид (C + доставка через бота + обмен контактами)** | Источник истины — наш `messaging`; каналы — Mini App, бот, потом iOS | Контроль и переносимость C; нативная доставка в Telegram; контакты — после договорённости, по явному действию каждой стороны | Нужно поддерживать несколько каналов доставки одного сообщения |

## Решение

Выбираем **D — гибрид**. Внедряем по этапам.

**MVP**

- **Модуль `messaging`** (`conversations`, `participants`, `messages`) — единственный источник истины для переписки. Диалог создаётся:
  - на отклик (`kind=job_response`): первое сообщение — сам структурированный отклик (цена, срок, текст);
  - на прямое обращение из каталога (`kind=direct`).
- **Экран диалога в Mini App:** текст, история, отправка с `client_msg_id` для идемпотентности. Обновление — поллинг раз в 3–5 с, пока экран открыт.
- **Уведомления о новых сообщениях через бота:**
  - превью, контекст («Заявка: повесить люстру») и кнопка «Ответить», которая открывает диалог в Mini App;
  - дебаунс: несколько сообщений подряд — одно уведомление;
  - если адресат сейчас смотрит этот диалог, уведомление не шлём.
- **Контакты — только после договорённости** (это и есть наш double opt-in):
  - пока сделка не в статусе `agreed`, кнопки «Поделиться контактом» нет;
  - телефоны, ссылки и @username в сообщениях до сделки автоматически маскируются с подсказкой «контакты откроются после договорённости»;
  - после `agreed` у каждой стороны появляется кнопка «Поделиться контактом»: каждый делится своим, явным действием. Это Telegram-ссылка (если есть username) или телефон через `requestContact`;
  - каждое раскрытие пишется в `contact_shares`.
- **«Договорились».** Если исполнителя выбирают по отклику, сделка сразу создаётся в статусе `agreed`. При прямом обращении из каталога кнопка «Договорились» в диалоге создаёт сделку `proposed`; вторая сторона подтверждает её в течение 72 ч, и сделка переходит в `agreed` ([ADR-0016](0016-trust-safety-and-reviews.md)).
- **Автопроверки** сообщений: маскирование контактов до сделки, ссылки, «предоплата на карту», стоп-слова. Результат — предупреждающий баннер получателю и сигнал в `moderation`.

**v1**

- **Ответ прямо из бота** (relay без топиков):
  - уведомление содержит контекст; ответ реплаем на него (`reply_to_message_id` → диалог) или после кнопки «Ответить здесь», которая делает диалог активным (состояние в FSM, TTL 15 мин);
  - бот подтверждает «→ отправлено Марко (Люстра)».
- **Realtime в Mini App:** SSE-поток событий `message.new` и `message.read` с fan-out через Valkey pub/sub. Поллинг остаётся запасным путём.
- **Фото в сообщениях** — через тот же media-конвейер.
- **Автоперевод ru ↔ sr** по кнопке «Показать перевод» с кэшем в `platform.translations`. Это одна из киллер-фич: русскоязычный клиент и сербский мастер понимают друг друга.

**Этап 2 (iOS/Android)**

- Нативный экран чата на том же API.
- Push через APNs/FCM — ещё один адаптер модуля `notifications`.

**Не делаем:**
- relay через топики — пока продаём что-либо за Stars в этом боте (комиссия 15%);
- Business-ботов на личных аккаунтах специалистов (доступ к личной переписке, строгий раздел 5.4 ToS).

## Последствия

**Положительные**

- Работает для пользователей без username. Контакты не раскрываются до договорённости и без явного действия владельца.
- Переписка — сигнал для антифрода и подтверждения сделок; споры разбираются по фактам.
- iOS-приложение получает готовый backend чата: остаётся только UI.

**Отрицательные и риски**

| Риск | Смягчение |
|---|---|
| Чат в MVP — это +1,5–2 недели работы по сравнению с вариантом A | Минимальный объём: только текст, поллинг, без статусов «печатает». Если сроки MVP критичны, экран диалога можно отложить: сообщения в MVP тогда ходят только через уведомления бота с ответом в Mini App-форме. Вынесено в открытые вопросы |
| Пользователи всё равно уйдут в личку Telegram | Это нормально после договорённости: сделка и отзыв уже зафиксированы в платформе, а обмен контактами — наш же механизм. Маскирование контактов до сделки защищает от спама и увода клиентов в самом начале |
| Лимиты Telegram на уведомления о сообщениях (1 msg/s на чат) | Дебаунс и группировка |
| Персональные данные в переписке | Переписка хранится 12 месяцев после последнего сообщения закрытого или неактивного диалога, затем удаляется задачей `platform.retention_sweep`. Legal hold действует для диалогов с открытыми жалобами и спорами. Доступ модераторов — только по жалобе и с записью в аудит |

**Что сделать**

- API `messaging` сразу проектировать под три клиента: Mini App, бот, мобильный. Курсорная история, `client_msg_id`, события для realtime.
- Правила автопроверок сообщений — в `moderation.content_rules` с категорией `contacts` и `scam`.

## Поправка 2026-10-04: пара договорилась однажды — контакты открыты

**Решение владельца** (2026-10-04, QUESTIONS.md № 36, «оставляй контакты открытыми»): если эта пара уже договаривалась — в любом диалоге, — контакты открыты.

- **Было.** Контакты открывала *текущая* сделка диалога: `agreed`, под спором или `completed`. «Договориться снова» (6.4) создаёт новую сделку `proposed`, и контакты закрывались снова: новые телефоны в сообщениях маскировались, «Поделиться контактом» отвечало 409, Telegram второй стороны пропадал из шапки. То же — после отмены договорённости и в новом прямом диалоге, который открывает «Заказать снова» (6.2): там номера снова скрывались до новой договорённости.
- **Стало.** Контакты в диалоге открыты, если его текущая сделка `agreed`, `disputed` или `completed` **или** эти двое — клиент и исполнитель диалога — когда-то договорились в любой своей сделке: по отклику или в чате, в этом диалоге или в другом, в любой роли. Сделка могла потом завершиться, отмениться или уйти в спор.
- **Не в счёт.** Предложение «Договорились», которое отклонили, отозвали или которое истекло: контактов оно не открывало. Другой пары это тоже не касается: другой клиент того же мастера его контактов не видит.
- **Почему.** Владелец хочет, чтобы повторный заказ у знакомого мастера шёл без трения: стороны уже знают друг друга и, скорее всего, обменялись контактами. Прятать номера снова — лишнее трение. Сделка и отзыв при этом уже в платформе.
- **«Поделиться контактом».** Раскрытие по-прежнему пишется в `contact_shares` по сделке диалога, поэтому в диалоге, где сделки ещё нет, делиться не по чему — кнопки нет, API отвечает 409. Номера в сообщениях там уже не скрыты, Telegram второй стороны виден.
- **Как.** Признак — `deals.agreed_at`: ставится при `agreed` и не стирается. Фасад `DealsApi.ever_agreed_pair` и `agreed_pairs` (пачкой — для списка диалогов), частичный индекс `ix_deals_ever_agreed_client_id_performer_id` (миграция `deals_0004`). Карточка диалога отдаёт `contacts_open`: Mini App не выводит правило из статуса сделки сам.
