## Правила обращения с секретами

**1. В git секреты не попадают никогда.**
- С шага 0.1 в `.gitignore` лежат: `.env`, `.env.*` (кроме `.env.example`), `*.pem`, `*.key`, а также файлы Terraform `*.tfstate`, `*.tfstate.*`, `.terraform/`, `*.auto.tfvars`. Проверка: `git check-ignore -v backend/.env infra/terraform/stage/.env` срабатывает на оба файла.
- В репозиторий коммитится только `backend/.env.example` с пустыми значениями.
- Хук pre-commit с gitleaks не даёт закоммитить секрет. Если секрет всё-таки попал в коммит (даже не отправленный на GitHub), его сразу ротируют. Переписывание истории ротацию не заменяет.
- Коммиты делаются только с вашего согласия.
- Способ хранения секретов stage и prod — решение Q1, оно нужно к шагу 0.25c. До него секреты stage не оформляем, кроме токенов Terraform в `infra/terraform/stage/.env` (0.25a–0.25b).

**2. Что считается чатом и где он хранится.**
- Чат — это всё, что видит ассистент: ваши сообщения и вывод команд, которые он запускает, в том числе команд, набранных в чате через `!`.
- История хранится открытым текстом на этой машине, в `~/.claude/projects/…/*.jsonl`, и передаётся провайдеру модели для обработки. Значение, попавшее в чат, считаем вышедшим за пределы менеджера паролей.
- **В чат можно:** dev-ключи и не секреты, по колонке «В чат» в сводке. Dev-ключи я кладу в `backend/.env`, не вывожу в терминал и не коммичу.
- **Stage- и prod-значения** вы вписываете сами, в отдельном окне Терминала, по разделу [«Как вписать секрет»](#как-вписать-секрет).
- **Не присылать никогда:** пароли от аккаунтов, коды 2FA и коды восстановления, приватные SSH- и age-ключи, JSON-ключи сервисных аккаунтов, любые stage- и prod-токены.
- **Можно открыто:** домен, Cloudflare Account ID, @username ботов, числовые Telegram id, chat_id, логин GitHub, публичный SSH-ключ (`ssh-ed25519 …`), публичный age-ключ (`age1…`), DSN Sentry (он всё равно попадает в браузерный бандл) и ключ PostHog (ключ приёма событий, доступа к данным не даёт).
- Команду `gh secret set ИМЯ --body значение` не используйте: значение попадёт в историю shell.

**3. Ассистент работает на той же машине.** У него есть shell вашей учётной записи, поэтому технически он может прочитать любой ваш файл. Запрет ниже — правило поведения, а не техническая граница. Защищаемся раскладкой файлов и запретом на команды, которые печатают секреты.
- `backend/.env` — только dev. Инфраструктурные токены лежат в `infra/terraform/<env>/.env`, stage- и prod-секреты — в GitHub или SOPS. Тогда `docker run --env-file backend/.env` в шаге 0.23 не унесёт в контейнер ничего, кроме dev.
- Ассистенту **запрещены** команды, которые выводят значения секретов:
  - `cat`, `less`, `head`, `tail`, `grep` без `-c` или `-q` по `.env`-файлам, `keys.txt`, `~/.ssh/id_*`;
  - `env`, `printenv`, `export -p`, `set` без аргументов, `echo $ТОКЕН`;
  - `set -x` и `bash -x` в скриптах, которые работают с секретами; `curl -v` с заголовком авторизации;
  - `docker inspect`, `docker compose config`;
  - `kamal secrets print`, `kamal app exec env`;
  - `terraform output`, `terraform show`, `terraform state pull`;
  - `sops -d` и `sops decrypt` с выводом в терминал;
  - `security find-generic-password -w` и чтение из CLI менеджера паролей в терминал.
- Проверяется только **наличие** значения: `grep -c '^TELEGRAM_BOT_TOKEN=.' backend/.env` (1 — задано, 0 — нет) или `make secrets-check`, который печатает «задан» или «пуст» по каждому имени.
- Если Claude Code спрашивает разрешение на команду из этого списка, отклоняйте.
- Если значение всё же попало в вывод, ассистент сразу говорит об этом. Stage- и prod-ключ ротируется немедленно, dev-ключ попадает в список K43.
- Если prod-значений на диске не должно быть вовсе, их можно подставлять из менеджера паролей в момент запуска: у 1Password и Bitwarden есть CLI (решение Q15).

**4. Раздельные ключи по окружениям.** У dev, stage и prod свои:
- боты (у каждого свой токен и свой адрес Mini App);
- чаты модераторов (K29);
- бакеты и S3-ключи R2 (у dev вместо R2 локальный Garage);
- проекты Hetzner и их токены;
- deploy SSH-ключи stage и prod;
- проекты или workspaces с ключами OpenAI и Anthropic, с лимитами расходов;
- ключи подписи JWT, пароли БД, ключ HMAC;
- age-ключи (при SOPS).

Ключ одного окружения не используется в другом. В dev по умолчанию работают фейковые AI-адаптеры, чтобы не тратить деньги.

**5. Минимальные права.** Каждый токен ограничен тем, что ему нужно:
- токен Cloudflare — вашим аккаунтом и зоной;
- ключ R2 — бакетами своего окружения;
- ключ OpenAI — только модерацией (K25);
- токен GitHub для ассистента — только репозиторием `specialist_app` (K3), PAT для GHCR — только чтением пакетов;
- S3-ключи Hetzner действуют на все бакеты проекта, поэтому бакет бэкапов живёт в отдельном проекте (K36).

**6. Кто генерирует секреты.**
- **Dev** — я, командой `make secrets-dev`, сразу в `backend/.env` и без вывода: ключи JWT, пароли ролей БД, ключи Garage, ключ HMAC.
- **Stage и prod** — скрипт пишу я, а запускаете вы в своём окне Терминала: `make gen-secret NAME=… ENV=stage|production`. Скрипт создаёт случайное значение и показывает его один раз. Вы сохраняете его в менеджер паролей (K10a) и подтверждаете. После этого скрипт сам записывает значение в GitHub или SOPS-файл и очищает экран. Так создаются:
  - ключи подписи JWT с `kid`;
  - `secret_token` вебхука Telegram;
  - пароли суперпользователя `postgres` и ролей `app`, `migrator`, `readonly`, `backup`;
  - **пароли шифрования pgBackRest, свой для каждого репозитория бэкапов (Hetzner и B2)**;
  - ключ HMAC для хэшей удалённых аккаунтов (`APP_HASH_KEY`; без него stage и prod не стартуют, менять нельзя — хэши «забудутся»);
  - deploy SSH-ключи stage и prod;
  - age-ключи при SOPS (K18).
- Пока копии в менеджере паролей нет, секрет stage или prod не считается заведённым.

**7. Ротация.**
- *Плановая* (ARCHITECTURE §13.5): токены ботов, ключи JWT (новый `kid`; старый живёт, пока не истекут access-токены, — 15 минут), ключи R2.
- *Перед публичным запуском*: всё, что когда-либо проходило через чат (K43).
- *При подозрении на утечку* (токен в скриншоте, публичном чате, логе, коммите, выводе команды) — сразу:
  - бот: @BotFather → `/revoke` → выбрать бота → новый токен в `.env` или в секреты → перезапуск процессов `bot`, `web`, `worker`;
  - Cloudflare, R2, Hetzner, OpenAI, Anthropic, GitHub: в том же разделе, где ключ создавался, удалить (Revoke/Delete) старый и выпустить новый;
  - SSH-ключ: убрать с серверов через Terraform;
  - age-ключ (при SOPS): новый ключ и перешифровка файлов;
  - после любой ротации: обновить `.env` или секреты, копию в менеджере паролей и сделать redeploy.
- Отозванные значения остаются в старых транскриптах (`~/.claude/projects/…`). После K43 эти файлы можно удалить, но тогда сессии из них нельзя будет продолжить. Если не удаляете, риск принимаем явно: в них лежат только недействительные ключи.

  Порядок действий опишет runbook «ротация секретов» (`infra/runbooks`).

**8. 2FA и менеджер паролей** на всех аккаунтах проекта (K10), копии секретов stage и prod (K10a).

**9. В логах секретов нет.** `initData`, токены, телефоны и тексты сообщений маскируются процессором логов (§13.5).

## Как вписать секрет

`make secrets-dev` появится в шаге 0.3. `make secret` (цели `dev`, `tf-stage`, `tf-prod`) и `make secrets-check` — в шаге 0.4. Цели `stage` и `production`, `make gen-secret` и `make gen-age` — в шаге 0.25c, по решению Q1. Раньше секреты не нужны.

**1. Откройте Терминал.** Нажмите ⌘ + пробел, наберите «Терминал» (или Terminal) и нажмите Enter. Это отдельное окно, не чат с ассистентом: ассистент не видит, что вы в нём вводите. Команды из этого раздела не набирайте в чате через `!`, иначе вывод попадёт в историю.

**2. Перейдите в проект:** `cd ~/PycharmProjects/specialist_app` и Enter.

**3. Впишите значение:**

```
make secret NAME=TELEGRAM_BOT_TOKEN TARGET=dev
```

- `TARGET=dev` — в `backend/.env`;
- `TARGET=tf-stage` или `tf-prod` — в `infra/terraform/stage/.env` или `infra/terraform/prod/.env`;
- `TARGET=stage` или `production` — в GitHub environment (через `gh secret set --env`) или в SOPS-файл, в зависимости от решения Q1.

Скрипт попросит вставить значение. Вставьте его через ⌘V. **Символы при вводе не отображаются, так и должно быть.** Нажмите Enter. Скрипт ответит, например, «TELEGRAM_BOT_TOKEN записан в backend/.env (46 символов)» и больше ничего не напечатает. Если длина не та, что вы ожидали, повторите команду.

**4. Проверьте:** `make secrets-check` покажет список имён со статусом «задан» или «пуст», без значений.

**Секрет GitHub через браузер**, если так удобнее: репозиторий → Settings → Environments → `stage` или `production` → Environment secrets → Add secret → Name и Value → Add secret. На плане Free, где environments нет: Settings → Secrets and variables → Actions → New repository secret. Риски Free описаны в K19.

**Вручную в файл — только если скрипт недоступен.** `.env` — скрытый файл, Finder его не показывает (⌘⇧. включает показ скрытых файлов). Открывайте его в PyCharm, а не в TextEdit: TextEdit заменяет прямые кавычки на «умные» и портит значение. Формат строки: `ИМЯ=значение`, без пробелов вокруг `=` и без кавычек.

**SOPS (только при Q1(а)).** `sops edit` открывает редактор vim, осваивать его не нужно: `make secret TARGET=stage` запишет значение в SOPS-файл сам.

### K10a. Копия секретов stage и prod в менеджере паролей
- **Что:** копия каждого секрета stage и prod в вашем менеджере паролей, сделанная в момент создания секрета.
- **Зачем:** секреты GitHub нельзя прочитать обратно, а сервер может погибнуть. Без копии:
  - **потерян пароль шифрования pgBackRest** — оба репозитория бэкапов (Hetzner и B2) не расшифровать, данные founding-специалистов не восстановить, RPO и RTO теряют смысл. Это единственный незаменимый секрет;
  - потерян ключ HMAC — таблица хэшей удалённых аккаунтов (антифрод, 12 месяцев) становится бесполезной;
  - потеряны пароли ролей БД — нельзя восстановить сервер вручную или перенести CI;
  - остальное (токены ботов, ключи R2, JWT, deploy-ключи) можно перевыпустить, но с копией авария проходит быстрее.
- **Когда:** с первого секрета stage (шаг 0.25a, токен Hetzner). Для бэкапов — обязательно к шагу 3.2 (≈ 2026-12-07).
- **Как:**
  1. Завести в менеджере паролей две папки (хранилища): `specialist-stage` и `specialist-prod`.
  2. Секреты, которые создаёт `make gen-secret` (правило 6), сохранять в момент генерации: значение показывается один раз. Если у менеджера есть CLI, скрипт может записывать в него сам.
  3. Ключи из веб-интерфейсов (Cloudflare, R2, Hetzner, B2, OpenAI, Anthropic, BotFather) сохранять сразу при создании: они тоже показываются один раз.
  4. Обязательный список:
     - пароли шифрования pgBackRest для каждого репозитория: `repo1-cipher-pass` (Hetzner) и `repo2-cipher-pass` (B2);
     - S3-ключи обоих репозиториев бэкапов;
     - пароли суперпользователя `postgres` и ролей `app`, `migrator`, `readonly`, `backup`;
     - ключи JWT и HMAC;
     - токены ботов;
     - приватные age-ключи (при SOPS).
- **Готово, когда:** в шаге 3.2 бэкап расшифрован и восстановлен с паролем шифрования, взятым из менеджера паролей, а не с сервера. В runbook `infra/runbooks/restore.md` записано, где лежит копия. Это критерий приёмки шага 3.2.
- **Прислать:** «копии есть» по списку, без значений.
- **Стоимость:** 0.

### K12. API-токены Cloudflare: для Terraform и для CI
- **Что:** два токена. Один для Terraform (широкие права), второй для CI (только деплой Worker'а Mini App).
- **Зачем:**
  - Terraform создаёт DNS-записи, бакеты R2 с CORS и lifecycle, маршруты Mini App, приложение Access, одно бесплатное rate-limit-правило, WAF-исключение для webhook Telegram и сертификат для сервера;
  - CI деплоит Mini App командой `wrangler deploy`.
- **Когда:** токен `terraform` — шаг 0.25b, перед запуском Terraform для Cloudflare; токен `ci-wrangler` — шаг 0.25d.
- **Как:** dash.cloudflare.com → иконка профиля справа вверху → My Profile → API Tokens → Create Token → Create Custom Token. Каждое право выбирается тремя списками: тип | ресурс | уровень.
  - **Токен `terraform`:**
    - Account | Workers R2 Storage | Edit — бакеты R2, CORS, lifecycle;
    - Account | Workers Scripts | Edit — привязка Worker'а Mini App к домену;
    - Account | Access: Apps and Policies | Edit — приложение Access для `admin.`;
    - Zone | DNS | Edit;
    - Zone | Workers Routes | Edit — маршруты Mini App и `/api`;
    - Zone | Zone WAF | Edit — WAF-исключение и rate-limit-правило;
    - Zone | Zone Settings | Edit — режим SSL, Always Use HTTPS;
    - Zone | SSL and Certificates | Edit — сертификат Origin CA (см. ниже).

    Account Resources: Include → ваш аккаунт. Zone Resources: Include → Specific zone → ваш домен.
  - **Токен `ci-wrangler`.** Маршруты и домен Worker'а заводит только Terraform, в конфиге wrangler их нет, поэтому CI хватает двух прав:
    - Account | Workers Scripts | Edit;
    - Account | Account Settings | Read.

    Если wrangler попросит больше, берём шаблон «Edit Cloudflare Workers» и ограничиваем его вашим аккаунтом и зоной.
  - Continue to summary → Create Token → скопировать токен (он показывается один раз) → сразу в менеджер паролей (K10a).

  Названия прав в интерфейсе могут отличаться, при создании сверимся вместе.
- **TLS между Cloudflare и сервером.** Режим Cloudflare — Full (strict): Cloudflare проверяет сертификат kamal-proxy. Предлагаем сертификат Cloudflare Origin CA: его выпускает Terraform, срок до 15 лет, kamal-proxy получает его из секретов, а выпускать Let's Encrypt через прокси Cloudflare не нужно. Поддержку своего сертификата в kamal-proxy проверим на версии Kamal в 0.25c. Альтернатива — Let's Encrypt в kamal-proxy, тогда право SSL and Certificates не нужно. Окончательно решаем в 0.25c; если возражений нет, берём Origin CA.
- **Прислать:** в чат не присылать.
  - `terraform`: `make secret NAME=CLOUDFLARE_API_TOKEN TARGET=tf-stage` (файл `infra/terraform/stage/.env`), к шагу 3.1a — тот же токен с `TARGET=tf-prod`. Токен даёт доступ и к prod-зоне, поэтому обращаемся с ним как с prod-секретом. Если Terraform переедет в CI (Q14), токен переносится в environment `production`;
  - `ci-wrangler`: секрет `CLOUDFLARE_API_TOKEN` в environments `stage` и `production` (K19).
- **Стоимость:** 0.

### K15. SSH-ключи и способ доступа к серверам
- **Что:** ваш публичный SSH-ключ и решение Q13 о том, как CI попадает на серверы.
- **Зачем:** SSH на серверы — только по ключу (ADR-0015). Раннеры GitHub Actions ходят с меняющихся IP, поэтому при IP allowlist деплой из CI не пройдёт. Нужен Tailscale или открытый 22-й порт только по ключу.
- **Когда:** ваш публичный ключ — шаг 0.25a, до Terraform; deploy-ключи для CI — шаг 0.25c.
- **Как** (в своём Терминале, см. «Как вписать секрет», п. 1):
  1. Проверить, есть ли ключ: `ls ~/.ssh/id_ed25519.pub`. Если файл есть, новый не создавать.
  2. Если ключа нет: `ssh-keygen -t ed25519 -C "owner"` → Enter (путь по умолчанию) → задать пароль к ключу. При вводе пароля символы не отображаются.
  3. `cat ~/.ssh/id_ed25519.pub` → прислать строку, которая начинается с `ssh-ed25519`. Это публичная часть, её можно присылать.
  4. Приватный файл `~/.ssh/id_ed25519` не отправлять никому.
  5. Deploy-ключи для CI — **отдельные для stage и для prod**. Их создаёт `make gen-secret` в вашем окне Терминала: приватная часть уходит в секрет `DEPLOY_SSH_KEY` своего environment (K19) и копией в менеджер паролей, публичная — на серверы через Terraform. Утечка stage-ключа тогда не открывает prod.
  6. Если в Q13 выбран Tailscale: аккаунт Tailscale с 2FA и auth key для GitHub Action. Auth key — секрет, его место в секретах environment.
- **Прислать:** публичный ключ и ответ по Q13.
- **Куда:** публичные ключи — в Terraform (в git можно), приватные deploy-ключи — в секреты GitHub.
- **Стоимость:** 0. Цена Tailscale в документах не указана.

### K19. Значения в секретах GitHub Actions
- **Что:** секреты деплоя и runtime-секреты stage и prod. Раскладка зависит от Q5.
  - **Pro или Team (рекомендуем).** Два environment: `stage` и `production`. У каждого в Deployment branches and tags стоит только `main`. Секреты окружения лежат в своём environment под одинаковыми именами (`TELEGRAM_BOT_TOKEN` есть и в `stage`, и в `production`). Их получает только job, который объявил этот environment и запущен из `main`. PR-прогоны веток `step/*` секретов окружений не видят.
  - **Free.** Environments для приватного репозитория недоступны, остаются секреты уровня репозитория с префиксами `STAGE_…`, `PROD_…`. **Риск:** их получает любой workflow в любой ветке, включая ветки `step/*`, которые пушит ассистент. Ошибочная или невнимательная правка workflow в ветке может вывести prod-токен бота, ключи R2 и deploy-ключ с root-доступом к prod ещё до вашего ревью. Префикс ничего не изолирует. Поэтому на Free prod-секреты в GitHub не кладём: Q1(а) с prod-ключом только у вас или Q1(в).
  - **Секреты уровня репозитория** — только то, что не открывает окружения, например `SENTRY_AUTH_TOKEN` для source maps. Проверкам PR секреты не нужны.

  Список для environment `stage` и `production`:

  - `CLOUDFLARE_API_TOKEN` — токен `ci-wrangler` (K12);
  - `KAMAL_REGISTRY_PASSWORD` — только если нужен PAT (K16);
  - `SOPS_AGE_KEY` — только при Q1(а), свой ключ в каждом (K18);

  - `HCLOUD_TOKEN` проекта `specialist-backup` — там restore-тест создаёт временную VM (K36);

## Что я делаю сам, без вас

Чтобы было видно, где ваше участие не нужно:
- генерирую dev-секреты (`make secrets-dev`): ключи JWT, пароли ролей БД, ключи Garage, ключ HMAC — сразу в `backend/.env`, без вывода;
- пишу скрипты `make secret`, `make gen-secret`, `make gen-age` и `make secrets-check`, которыми вы вписываете и создаёте секреты stage и prod;
- выставляю кнопку меню dev-бота через Bot API; имя, описания и команды ботов на ru, sr и en выставляю скриптом (`setMyName`, `setMyDescription`, `setMyShortDescription`, `setMyCommands`);
- описываю в Terraform VM, firewall, DNS, бакеты R2 с CORS и lifecycle, Access, rate-limit, WAF и сертификат для сервера;
- настраиваю webhook stage- и prod-ботов при деплое;
- пишу черновики текстов, таксономии, словаря стоп-слов и переводов;
- после каждого шага сообщаю, что проверить и какой командой;
- значения секретов не вывожу и не читаю, проверяю только их наличие (правило 3).

Только вы:
- регистрируете аккаунты, включаете 2FA и привязываете карты;
- делаете всё в BotFather (включая Main Mini App и inline mode, если он понадобится);
- выполняете в браузере вход `cloudflared tunnel login` и `gh auth login` (или создаёте токен для `gh`);
- создаёте секреты stage и prod своей командой и сохраняете копии в менеджер паролей (K10a);
- вписываете stage- и prod-значения в `.env` для Terraform, в секреты GitHub или в SOPS;
- вводите пароль своей учётки в админке;
- проверяете на телефонах;
- даёте согласие на каждый коммит.
