# Нагрузочный прогон (DEVELOPMENT_PLAN 8.3)

Цель — подтвердить SLO [ARCHITECTURE §2.4](../ARCHITECTURE.md#24-нефункциональные-требования-slo) с
запасом до запуска: пиковый RPS через 12 месяцев (30–60, [§2.3](../ARCHITECTURE.md#23-ожидаемая-нагрузка)) ×2
на stage, увеличенном до размера prod.

Код: сценарии k6 — [`infra/loadtest`](../../infra/loadtest), цели — `make/loadtest.mk`, фейковый
отправитель Telegram — `backend/src/app/platform/telegram/fake_sender.py`, initData пользователей —
`cli loadtest-initdata`.

## SLO и пороги k6

| Что | SLO (§2.4) | Порог k6 | Где смотреть |
|---|---|---|---|
| Латентность API на сервере | p95 < 150 мс, p99 < 400 мс | `http_req_duration{slo:api}` | итог k6, дашборд (3.3) |
| Поиск в каталоге | p95 < 200 мс | `http_req_duration{slo:search}` (выдача, счётчик, подсказки) | итог k6, дашборд |
| Ошибки | < 0,1% | `http_req_failed` < 0,001, `checks` > 0,999 | итог k6, Sentry |
| Уведомление о новой заявке | p95 < 2 мин от публикации | — (k6 не видит доставку) | метрики уведомлений, дашборд |
| Лаг read-model поиска | p95 < 10 с | — | метрики проекций, дашборд |

k6 меряет латентность у себя, с сетью до stage, а SLO — на сервере. Пороги k6 поэтому строже
SLO; если провал — в пределах сети, решает серверная гистограмма на дашборде (3.3). Сеть можно
учесть явно: `NET_MS=<RTT до stage-api, мс>` добавляется ко всем порогам.

Бизнес-отказы отклика (мест нет, уже откликался, суточная квота, заявку закрыли) — не ошибки:
их считает метрика `respond_refused`.

## Сценарии

| Сценарий | Что делает | Доля RPS |
|---|---|---|
| `login` | `POST /auth/telegram` с initData; свои пользователи, не из пула | 9 в минуту — лимит `/auth/*` 10/мин на IP |
| `catalog` | выдача специалистов (текст, категория, «доступен сегодня»), счётчик, подсказки, карточка, справочник | 40% |
| `feed` | лента заявок (с категорией и без), счётчик новых, карточка заявки | 25% |
| `respond` | отклик на случайную заявку ленты (`Idempotency-Key`) | 0,2 в секунду на 1×, 0,4 на 2× |
| `chat` | список диалогов, поллинг сообщений с `If-None-Match` (304) | 17% |
| `notifications` | бейджи таббара, список уведомлений | 17% |

Доли — допущение о смеси запросов Mini App. Профиль `load`: 2 мин подъём до 1× пика (`PEAK_RPS`,
по умолчанию 60) → `HOLD` (5 мин) → 2 мин подъём до 2× → `HOLD` → 1 мин спад, всего 15 мин.

Весь прогон идёт с одного IP, поэтому:
- setup() входит под `POOL` (60) демо-специалистами не чаще 9 в минуту — около 7 минут;
- каждый запрос берёт случайного из пула: лимиты каталога и ленты (120 в минуту на человека) делятся
  на весь пул, на 2× пика это ≈ 30 в минуту на пользователя;
- access-токены пула k6 не обновляет (refresh у VU, делящих пользователя, гонялся бы), поэтому на
  время прогона access живёт час (`STAGE_LOADTEST`, ниже). Не хватит срока — setup() остановит прогон.

Данные — `seed-demo --scale lab`: 50 000 специалистов и 1 000 заявок. Пользователи прогона — эти
демо-специалисты (у них приняты согласия и опубликован профиль, поэтому они могут откликаться). Их
Telegram ID длиннее 52 бит: живой человек под ними не войдёт.

## Прогон на stage

Нужен stage из [stage-bootstrap](../../infra/runbooks/stage-bootstrap.md) и метрики 3.3 (дашборд).
Все команды — в своём Терминале.

1. **Увеличить VM** до размера prod (CX33; `cpuset-cpus` в `infra/kamal/deploy.yml` рассчитан на 2 ядра
   CX23 — на время прогона web можно дать `0-3`, иначе два новых ядра простаивают):
   ```
   make tf ENV=stage ARGS='apply -var stage_server_type=cx33'
   ```
   Hetzner перезагружает VM при смене типа (≈ 1–2 мин простоя stage).
2. **Режим прогона**: Variable environment `stage` `STAGE_LOADTEST` = `true`
   (Settings → Environments → stage → Variables), затем Actions → deploy-stage → `deploy` с текущим
   sha. В логе старта web — `telegram_fake_sender`: уведомления не уходят в Telegram, а ждут тот же
   лимитер Valkey и латентность Bot API; access-токен — час.
3. **Данные** (один раз на stage, ≈ десятки минут):
   ```
   ssh root@<STAGE_HOST> 'docker exec $(docker ps -qf label=role=web | head -1) sosed cli seed-demo --scale lab'
   ```
4. **initData** — прямо перед прогоном (годен час):
   ```
   STAGE_HOST=<ip> make loadtest-users ENV=stage
   ```
5. **Прогон** (≈ 7 мин входа + 15 мин нагрузки), с машины с хорошим каналом — не через мобильный
   интернет:
   ```
   STAGE_DOMAIN=<домен> make loadtest ENV=stage
   ```
   Отдельные сценарии — `SCENARIO=catalog,feed`; длиннее ступени — `HOLD=10m` (тогда проверьте срок
   токена). Цель — `https://stage-api.<домен>` напрямую, не `stage-app.`: Worker Mini App на
   бесплатном тарифе — 100 000 запросов в сутки, прогон съел бы их за полчаса.
6. **Во время прогона** — дашборд (3.3): p95/p99 по маршрутам, CPU и память VM, пул БД, очередь
   procrastinate, задержка доставки уведомлений, лаг проекций поиска; после —
   `pg_stat_statements` (топ по `total_exec_time`).
7. **Вернуть stage**:
   - `STAGE_LOADTEST` удалить (или `false`) и снова deploy-stage `deploy`;
   - `make tf ENV=stage ARGS='apply'` — тип из `terraform.tfvars` (CX23);
   - `make tf ENV=stage ARGS='plan'` — «No changes».

Если запросы отвечают 403 или challenge — Cloudflare принял k6 за бота: Security → Events, правило —
временное skip для IP машины с k6 на время прогона.

Отклики прогона остаются в базе stage и в очереди модерации (без AI-ключей — ручная очередь); это
демо-данные stage. Суточная квота откликов (10 на специалиста) за повторный прогон в тот же день
выберется — отказы уйдут в `respond_refused`, на пороги не влияют.

## Локально — только smoke

```
make loadtest ENV=local
```

2 VU, 30 с, только гостевые чтения (`catalog`, `feed`) против `http://127.0.0.1:8000` — проверка,
что сценарии и пороги работают. Входа нет: он создал бы сессии в базе dev. Полный профиль локально
make не запустит. На Маке владельца — через замок тяжёлых прогонов.

## Рассылка заявки 10 000 подписчикам

Пункт плана «рассылка через лимитер и фейковый отправитель (≈ 6 мин) не мешает приоритетным
уведомлениям» — отдельная проверка, k6 её не делает: нужны 10 000 подписок на заявки (5.7) у
демо-специалистов, а `seed-demo` их не создаёт. До сида подписок — вручную: опубликовать заявку в
популярной категории во время прогона и смотреть очередь доставки и задержку приоритетных
уведомлений на дашборде.
